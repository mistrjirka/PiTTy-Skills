# UX evaluation

Evaluate the user task, not whether a screen resembles a template.

For an existing application, compare the target with its parent shell and two similar nearby pages. Review layout width, gutters, typography, headers, controls, table/form density, navigation, status placement and responsive behavior. A polished but inconsistent page does not pass. Identify deviations using actual reference components or screenshots, not personal taste.

Check normal user-facing fields for unresolved GUIDs, internal codes, repeated headings and duplicate destinations. Verify real display-name lookup, helpful missing-name behavior and consistent list/detail terminology. Keep technical metadata only where it serves a real support or audit task.

Walk the relevant journey with representative content. Check discoverability of the next action, accurate feedback, error recovery, navigation, keyboard/focus behavior, readability and user control over consequential actions. Include slow, empty, failed and repeated operations.

Inspect the initial viewport with representative content at the actual device size. Can the user see the main content and next action without scrolling past avoidable chrome? Identify blocks devoted to identifiers, dates, status/source labels, decorative cards, repeated headings and empty padding. For each, ask what user decision it supports and whether it can be condensed, grouped, moved below the main content, disclosed on demand or removed. Preserve necessary context and accessibility; avoid arbitrary percentages or density targets. Recheck the rendered screen after changes, not only the component code.

Prioritize by evidence: blocked task or accessibility barrier; misleading result or loss of work; measurable friction; optional design improvement. Explain the affected user and concrete remedy. Unknown user behavior is a hypothesis to test, not a measured conversion claim.

Counts of fields, cards, columns or clicks are signals, not universal limits. Do not call a screen critical merely because it has twelve inputs or more than seven choices. Preserve legitimate expert workflows and dense data interfaces. Check the applicable accessibility requirements rather than imposing an arbitrary design quota.

For AI features, inspect disclosure, source support, correction/override, data handling and previews where actions are consequential. Do not invent confidence percentages or expose hidden reasoning.

Report what was inspected (source, screenshots, browser interaction, accessibility tools or user study) and what was not. A source inspection is not an observed usability test.
